NeuroFlow — end-to-end data flow, as built

Every piece of data in this app has a creator, a home, a reader, and usually a writer that changes it later. This document maps that movement so the logic can be re-derived and rebuilt: where the 10 Room tables and 104 preference keys come from, which of the 16 domain engines consumes them, what each engine produces, which of the 14 workers writes results back, and how ViewModels, screens, notifications, and widgets read the outcome.

Scope: current state of app/src/main/java/com/neuroflow/app/ at Room schema v20. Nothing here is a proposal. Claims carry file:line citations and a confidence label; the gaps and contradictions found while mapping are collected in the last section.

How to read these diagrams

One question per diagram. Colour tells you what kind of thing a box is; line style tells you how data moves. Dense graphs are also written as Graphviz sources (*.dot) for tooling.

source — enters from a human or the OS Room table DataStore preference key domain engine (pure logic) worker / actuator — runs in background, writes consumer — ViewModel, screen, notification, widget inert — written, never read back
read / call, synchronous, in-process write-back (a background job mutates stored data) observation (Room Flow pushes to UI) assumed / unsupported / dead path

Three facts that explain most of the rest

  • Scores are never stored; placements are. TaskScoringEngine recomputes on every call (domain/engine/TaskScoringEngine.kt:438). What is persisted are the inputs the engines feed themselves back in — 15 machine-written columns on TaskEntity and ~40 machine-owned preference keys.
  • There are no foreign keys, no cascades, and no DB triggers. Referential cleanup, recurrence rollover, streak counting, and scheduling gates are all hand-written in TaskRepository and the scheduler worker (data/local/entity/TaskEntity.kt — no @ForeignKey anywhere in 10 entities).
  • Storage is not the only source. Android usage-stats events and the system clock feed engines directly; nowMillis is injected as a default parameter in every pure engine so the logic stays testable (domain/engine/*.kt).

4. The energy chain from a sleep record to a slot being worth taking

Three rows, top to bottom: ground truth → circadian reservoir → usable energy. The last row forks — the app computes "energy" twice along two non-equivalent paths, and that difference is the single most important thing to know before changing any scheduling behaviour.

What this chain cannot currently do

Recorded in project memory from the energy model audit (2026-10) and confirmed by the code above. high confidence — see ENERGY_PRODUCTIVITY_AUDIT.md.

  • The reservoir decays over 960 minutes from a peak that is itself inferred. With circadianFactor floored at 0.35 and confidence multiplying the peak term, the maximum reachable usableEnergy for a typical detection is well under 100; combined with the fatigue subtraction, the "deep work now" recommendation band is mathematically hard to enter.
  • Sleep debt is invisible to the priority score. TaskScoringEngine never reads prefs.sleepPressurePoints; only the planner and the energy model do. So a exhausted user still sees the same "do this first" ordering, and only the placement of it changes.
  • Two live-energy numbers exist and they disagree. Path A (UI) evaluates at now; Path B (scheduler) evaluates at the slot time and then blends Path A back in with a weight that collapses to 0 beyond 12 hours. Anything that shows "energy" and anything that decides "when" are not reading the same quantity.
  • Manual peak override short-circuits everything. manualPeakProfileEnabled supplies a profile with confidence = 1f, bypassing the abstention, freeze guard, and auto-tune gates that would otherwise police the inferred windows.

10. Rebuild checklist the invariants, if you were to write this again

Not a proposal to change anything → this is the load-bearing behaviour the current design depends on, stated so it survives a rewrite. Each item names the file that proves it exists today.

#InvariantWhy the app breaks without it
1Ownership flag on every placement. A block is either the user's or the machine's, recorded explicitly (isAutoScheduled), and a user edit must clear it plus the cooldown timestamp.Otherwise the scheduler overwrites manual plans, and after a manual edit the plan still "belongs" to automation, so it moves back. AutoSchedulingContracts.kt:14, NewTaskFlowViewModel.kt:282
2Stability before optimisation. Ask "is this move worth disturbing the user for?" before asking "where is best". Unknowns worth validating before trusting this map further

  • Runtime behaviour. Everything here is static reading of source; no traces, no device, no emulator. Whether the tick loop actually survives Doze, and how often the single-instance guard fires, is unmeasured. low
  • Orphan navigation. Routes matrix, history, analytics, weekly_schedule have no in-app entry point, and com.procus.ACTION_OPEN_ANALYTICS is emitted by two callers but not handled in MainActivity.handleIntent. Either an external shortcut exists or these screens are unreachable. medium
  • Field counts. "104 preference keys" and "31 backed up" are read off the DataStore and codec sources; a rebuild should recount rather than reuse the number.
  • Which divergences are intentional. Several double-implementations may be deliberate (a presentation-grade formula kept simple on purpose). Nothing in the repo documents intent → there is no ADR or docs/ precedent, so intent is unknown, not absent.
